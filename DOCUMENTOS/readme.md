# Oficina de Valencia — Design System

A ground-up new design line for the Arco Seguros CRM — a sales & claims tool for an insurance brokerage (correduría de seguros). Tone: professional, modern, inspiring — a confident single-blue brand identity in place of the previous warm-terracotta system.

**Stack (reference):** Next.js + TypeScript + Tailwind CSS / CSS custom properties.

## Source material

This design system was built from three inspiration documents analyzed and synthesized by the design assistant: Apple, Tesla and Starbucks web design breakdowns (`guidelines/inspiration-sources.md`). None of the three is a CRM or application design system — all three are consumer marketing sites — so nothing here is a copy of any of them. What was extracted is documented per-decision throughout this readme and in `SKILL.md`.

**Brand decisions confirmed by Miriam (Arco Seguros):**
1. Blue as the single dominant/predominant brand color — chosen to read as professional and modern.
2. Corporate-trust blue tone (deep, confident — closer to Apple's Action Blue than Tesla's brighter Electric Blue).
3. Compact, efficient density — this is a daily-use productivity tool, prioritize rows-per-screen over airy whitespace.
4. Soft, layered shadows for elevation (not Tesla/Apple's near-flat approach) — needed for a CRM's real overlapping surfaces (dropdowns, modals, sticky headers).

## Reconciliación con ARC-36/ARC-37 (2026-07-19)

Este sistema se construyó originalmente a partir de los tres documentos de inspiración (`INSPIRACION/`), no a partir del brief de Linear — a diferencia del sistema Arco Seguros (terracota), que sí se construyó directamente desde los prompts de ARC-36/ARC-37. A petición de Miriam se revisó el contenido completo de ambos tickets de Linear contra lo ya construido aquí, y se resolvieron cuatro huecos encontrados:

1. **Tamaño táctil mínimo — ahora responsive.** ARC-36 es explícito: Mónica y Antonio usan la app a diario, con una mano, en movimiento, desde el móvil. `--tap-target-min` era 36px fijo (pensado solo para escritorio). Ahora es **44px por defecto** (móvil/táctil) y **36px a partir de `--breakpoint-desktop` (768px)** vía media query en `tokens/spacing.css` — mantiene la densidad compacta confirmada por Miriam para el uso de escritorio, sin penalizar el uso táctil real en el móvil. Se propaga automáticamente a cualquier componente que use el token (`Button`, `MainNav`), sin tocar su lógica.
2. **Color secundario — añadido, pero reservado.** ARC-36 pide explícitamente un color secundario. Se añadió `--color-secondary-*` (familia grafito-tinta, cromatismo muy bajo, mismo grupo de tono frío que los neutros) en `tokens/colors.css` — cumple el requisito del ticket sin reintroducir un segundo color que compita con el azul, respetando el principio de "un solo acento" ya confirmado por Miriam. **No está conectado a ningún componente todavía** — existe como base disponible si surge una necesidad real (p. ej. una superficie oscura), pero de momento el acento sigue siendo monocromático en la práctica. Marcado como reservado en el propio comentario del archivo.
3. **Icono de app + splash screen (PWA) — añadido.** `guidelines/app-icon-splash.html` y `guidelines/wordmark.html` son nuevos. Como no hay logo real (misma situación que el resto del sistema — ver "Brand assets"), el icono usa un monograma de texto "OV" (Inter 700) sobre `--color-primary-600`, con el splash siguiendo el mismo tratamiento y el color de tema de la barra de estado documentado como `primary-600`. Reemplazar en cuanto exista una marca real.
4. **Guía de iconografía — añadida.** `guidelines/iconography.html` documenta el set de iconos ya usado dentro de los componentes (SVG inline, trazo 1.75px, sin dependencia externa — la misma filosofía "zero-runtime-dependency" que ya regía `MainNav`/`DatePicker`) más los 5 iconos de canal (llamada/WhatsApp/correo/redes/web, ya usados en `ContactHistoryItem`) y 5 iconos de acción nuevos (editar/guardar/volver/añadir/buscar) que ARC-36 pide pero que ningún componente consume todavía — quedan definidos y listos para cuando aparezcan en un componente real. **Nota:** se optó deliberadamente por SVG inline en vez del CDN de Lucide que usa el sistema Arco Seguros, para mantener la coherencia con la arquitectura sin dependencias que ya tenía este sistema — no es una omisión, es la misma decisión aplicada de forma consistente.

**Lo que no se tocó:** la decisión de densidad desktop-first en sí (menos padding, más filas por pantalla) sigue siendo la que confirmaste — solo se corrigió el tamaño táctil, que es un tema de accesibilidad independiente de la densidad visual.

## Content fundamentals

- **Language:** Spanish (Spain), informal/professional register.
- **Tone:** confident and clear — this is a "modern institution" read, more composed than playful. Avoid marketing-speak; every label describes exactly what it does.
- **Casing:** sentence case throughout (buttons, headers, labels) — never ALL CAPS except tiny uppercase micro-labels (status badges), which use letter-spacing to signal "this is a tag, not a sentence."
- **Density:** short labels, minimal explanatory subtext — compact density means the UI should be scannable, not read line by line.

## Visual foundations

- **Color:** primary is a corporate-trust blue (`--color-primary-500`) — the single chromatic brand accent, used for the one primary action per screen, active nav state, links, and focus rings. Diluting the accent with a second competing hue was judged to weaken the "confident, modern" read (an Apple/Tesla cue), so `--color-secondary-*` (added 2026-07-19 for ARC-36 compliance — see "Reconciliación con ARC-36/ARC-37") is a near-neutral graphite-ink family, not a second brand hue — used narrowly for `ContactHistoryItem`'s channel icons, not as a competing accent. Neutrals are cool grays (not warm) to stay consistent with the blue-forward direction. All state colors are defined in OKLCH for perceptual evenness, picked so the 4 sale-status + 3 claim-status + 3 priority-status + 1 warning colors are mutually distinguishable and none collide with the brand blue's hue (~251–255).
- **Type:** one family — Inter. Hierarchy comes from weight and size, not from mixing families. Compact desktop-first scale (14px default body, versus a mobile-first system's typical 15–16px) since this is a data-dense tool read at a desk.
- **Spacing:** base-4 scale (4–64px), desktop-first. Compact row/control heights (40px standard button, 40px table row) to keep more rows visible per screen — the explicit trade-off requested over a more spacious/airy layout.
- **Backgrounds:** flat, cool off-white app background (`--surface-app`); no gradients, no photography, no textures. Visual interest comes from the blue accent and color-coded status badges, not decoration — the Apple/Tesla restraint principle.
- **Animation:** quick and functional — 120–240ms ease-out transitions. Universal press feedback is `transform: scale(0.97)` on every interactive control (button, badge-as-button, nav item) — a convergent cue found across all three inspiration systems, adopted here as the one signature micro-interaction.
- **Borders:** hairline 1px, `--border-default` (neutral-200) on cards and dividers; `--border-strong` for secondary-button outlines. No colored borders except semantic badges/overdue treatment.
- **Shadows:** whisper-soft, layered — 2 stacked low-alpha shadows rather than one heavy drop shadow (the Starbucks cue, cooled down). Cards use `--shadow-sm`; dropdowns/popovers use `--shadow-md`; modals/sheets use `--shadow-lg`. This is the one deliberate departure from Apple/Tesla's near-zero-shadow marketing-site approach — a CRM has real overlapping surfaces that need a functional depth cue those sites don't.
- **Corner radii:** small and precise by default (`--radius-xs` 4px inputs, `--radius-sm` 6px, `--radius-md` 8px cards) — a "technical/engineered" read closer to Tesla's 4px precision than Starbucks' universal 50px pill. Full pill (`--radius-pill`) is reserved for status badges and the primary action button only, so it keeps its meaning as an unambiguous "this is the one action / this is a tag" signal.
- **Transparency/blur:** used only for the modal/bottom-sheet backdrop (`--surface-overlay`) — no frosted-glass blur elsewhere.
- **Imagery:** none in this MVP — no photography or illustration requested.

## Accessibility

- Text and state-color combinations are tuned for AA contrast against their paired background.
- Minimum click target (`--tap-target-min`) is **responsive**: 44px on mobile/touch (default — matches ARC-36's one-handed, in-the-field usage), tightening to 36px from `--breakpoint-desktop` (768px) up for mouse/trackpad use, where the compact-density decision applies. Primary actions clear 40px regardless. See "Reconciliación con ARC-36/ARC-37".
- Focus states always render a visible ring (`--focus-ring`), never rely on color change alone.

## Brand assets

**No logo file was provided.** Per design-system policy, no logo was invented or approximated — wherever a mark would normally go, use the plain wordmark "Oficina de Valencia" (Inter 700) until a real mark exists (`guidelines/wordmark.html`). The app icon/splash treatment (`guidelines/app-icon-splash.html`, added 2026-07-19 for the PWA requirement in ARC-36) uses the same no-logo policy: a text monogram ("OV") on `--color-primary-600`, not an invented mark — replace the instant a real logo/icon exists.

## Correcciones de la auditoría PRD (2026-07-22)

El mismo día se hizo un repaso completo del CRM-PRD (Notion) punto por punto contra el estado real de Oficina de Valencia — las 14 funciones, los 5 modelos de datos y las 15 pantallas que implica el PRD (login + P1–P6 + 4 sub-pantallas + las 4 de este proyecto). Miriam pidió corregir 3 de los hallazgos:

1. **`screens/p6-posibles-clientes.html` — la pantalla que faltaba detrás de la pestaña "Posibles clientes".** `MainNav` tiene la sección "leads" desde el 2026-07-21 (Caveat §18), pero P6 nunca se había construido como archivo en este proyecto — la pestaña apuntaba a ningún sitio. Nueva pantalla: `SearchBar` + lista de `ClientRow` filtrada a `saleStatus: "interesado"`, cada fila con la acción "Convertir en cliente" (avanza el estado a `presupuesto` sin crear ningún registro nuevo, tal y como pide el PRD) y un botón "+ Nuevo" con `icon="add"` para dar de alta un posible cliente directamente en este estado. `EmptyState icon="search"` cubre la búsqueda sin resultados.
2. **`ReminderItem` gana `assignedTo`.** El hallazgo: D3 y la actualización del PRD del 16/07 piden asignación por persona, pero eso se resolvía solo filtrando por la pestaña activa de `Tabs` — la propia fila no mostraba de quién era el recordatorio, así que una vista combinada (todas las personas a la vez) sería ilegible. La prop es opcional y se imprime tras la fecha ("22 jul · Antonio"); se dejó fuera a propósito de vistas ya filtradas a una sola persona, donde sería redundante. `screens/f6-alertas-renovacion.html` ahora pasa `assignedTo` en sus 4 recordatorios de ejemplo.
3. **Nuevo componente `SortToggle`.** El hallazgo: ARC-34 (ya Done en Linear) pide prioridad "visible, filtrable y ordenable" en P2 — `FilterChip` ya cubría "filtrable", pero ningún componente ni guideline representaba "ordenable". `SortToggle` es un botón mínimo (etiqueta + chevron que rota) que alterna asc/desc; deliberadamente no es una cabecera de tabla completa, porque las listas de este sistema son filas/tarjetas, no columnas de una `<table>` literal con algo a lo que alinear una cabecera. Se conectó de verdad (no solo decorativo) en `screens/f9-clientes-frios.html`, ordenando por "Días sin contacto" — cuando se construya P2, debería reutilizarse el mismo componente para su columna de prioridad en vez de inventar un segundo control.
